# 1. このドキュメントについて

AIエージェントによる開発の仕組み(ソフトウェアファクトリー)を、別の環境で作り直すための設計書です。元になった実装は、元の非公開リポジトリの michiomochi 環境(Hermes の default プロファイル)です。環境ごとに値(DB 名、チャンネル、モデル、有効にするプラグイン)が違うので、それらは環境の設定(`envs/<名前>.toml`)で決めます。このドキュメントと [Notion の補足ページ](https://app.notion.com/p/2b336af62ba9fb1eb1e7c6a9b9f01946) を別のAIに渡すと、再現を始められます。前提として、再現先でも、タスクやエピックなどの管理は Notion で行い、AIを動かす環境は Hermes です。「SSOT」は、依頼、進捗、完了レポートを残す唯一の記録場所(Notion のデータベース)を指します。

| 項目 | 内容 |
|---|---|
| 仕組みの一言 | 依頼をSSOTに1行で登録すると、重複確認、カード化、工程ごとの実行、独立したAIレビュー、承認の依頼までが自動で進み、人は完了時の承認だけを判断します。 |
| 中心の考え方 | SSOTが唯一の正本。判断が要らない部分はAIを使わないスクリプトで動かす。AIの作業は、必ず別のAIが検証する。他の人への依頼などの外部への送信は、人が明示的に指示するまでしない。PRの作成・公開・マージとデプロイは、AIではなくスクリプトだけが行う。 |
| この版での軽量化 | 会社エピックと別プロジェクトの工程ガイドラインは外します。工程は5つ、人の承認は完了時の1つにします(11章)。 |
| 確認していないこと | リポジトリ内のスクリプト、プロンプト、スキルを読んでまとめています。別環境での再現は、まだ試していません。 |

# 2. 全体像

仕組みは、SSOT、実行キュー、実行役、レビュー役、定期ジョブの5つでできています。部品ごとに、現在の実装と、再現先での構成を並べます。

| 部品 | 役割 | 現在の実装 | 再現先での構成 |
|---|---|---|---|
| 作業SSOT | 依頼、進捗、完了レポートの唯一の正本。状態はSSOTの行だけで決まります。 | Notion のデータベース(タスク、エピック、ドキュメント、レビュー) | Notion のデータベース(同じ) |
| 実行キュー | 実行待ちのカード。SSOTの行とは別に、実行の順番と生死だけを持ちます。 | Hermes の kanban(ボード work-card) | Hermes の kanban(同じ) |
| 実行役 executor | カードを1枚ずつ受け取り、要件、設計、実装、テストを行います。 | Hermes のプロファイル executor | Hermes のプロファイル executor(同じ) |
| レビュー役 reviewer | 実行役の成果を独立して検証し、完了にするか差し戻します。 | Hermes のプロファイル reviewer(最も強いモデル) | Hermes のプロファイル reviewer(同じ) |
| 取り込み | 未着手の依頼を見つけて、カードにします。 | cron 取り込み(1分ごと、監視スクリプト付き) | Hermes の cron(同じ) |
| ゲート制御 | 工程の順番を守り、次の工程のカードを作り、承認の依頼を出します。AIは使いません。 | epic_gate_[controller.py](http://controller.py)(2分ごと) | リポジトリの scripts/ のスクリプトを使う |
| プランナー | エピックの完了条件に向けて、候補からタスクを作ります。 | cron 案件プランナー(5分ごと) | リポジトリの prompts/ の指示文を Hermes の cron に登録 |
| 監視 | 止まったカード、順番の違反、閉じ忘れを検出して直します。 | epic_pipeline_[health.py](http://health.py)(1分ごと) | リポジトリの scripts/ のスクリプトを使う |
| 人の判断の窓口 | 承認の依頼を1行ずつ並べ、人が状態を決めます。 | レビュー用データベースと ask_[human.py](http://human.py) | Notion のレビュー用データベース |
| 反映ジョブ | 人が決めた承認や差し戻しを、SSOTに反映します。 | cron レビュー結果の反映(3分ごと) | リポジトリの prompts/ の指示文を Hermes の cron に登録 |

## 2.1 AIを使う部分と使わない部分

定期ジョブは、監視スクリプトの出力が変わったときだけAIを起こします。順番を決める処理や警告の検出は、AIを使わないので、安く、間違えません。

| 処理 | AIの使用 | 理由 |
|---|---|---|
| 工程の順番、カード作成、承認の依頼 | 使わない | 規則が決まっていて、間違いが許されないためです。 |
| 止まりの検出、状態の変更の通知 | 使わない | 差分を取るだけで足りるためです。 |
| 取り込みの判断、プランナー、監視の対処 | 出力が変わったときだけ使う | 重複の判断や、原因の調査には判断が必要なためです。 |
| 要件、設計、実装、テスト、レビュー | 使う | 本来の作業です。 |

# 3. 作業の流れ

依頼をSSOTに1行登録してから完了までの流れです。軽量版では、エピックに属さない単発の依頼も同じ流れで動きます。

| 順 | 段階 | 担当 | 中身 |
|---|---|---|---|
| 1 | 登録 | 人またはAI | SSOTに行を作ります(状態は 未着手)。作業より先に行を作ります。 |
| 2 | 重複確認 | 取り込み(AI) | SSOT、実行キュー、開いているPRを検索します。同じ目的と範囲なら、カードを作らず、既存の作業にリンクします。 |
| 3 | カード作成 | 取り込み(AI) | カードの本文に、SSOTの行のURL、目的、完了条件を英語で書きます。SSOTを 進行中 にします。 |
| 4 | 実行 | executor | SSOTの行を読み、チェックリストを進めます。成果物は、先に文書として作ります。長い作業では、生きている印(heartbeat)を送ります。 |
| 5 | 自己点検 | executor | レビューを依頼する前に、複数の文書にある数字、名前、しきい値が同じか、前に書いた文と後ろの文が矛盾しないかを確認します。結果を作業メモに1行書きます。 |
| 6 | レビュー依頼 | executor | カードを レビュー待ち にして、再確認してほしい点を書きます。 |
| 7 | レビュー | reviewer | 自分で再実行して検証します。1回目に、必要な修正を全部まとめて差し戻します。2回目以降は、直したかどうかだけを見ます。 |
| 8 | 完了 | reviewer | チェックリストが全部チェック済みで、完了レポートに根拠があるときだけ、SSOTを 完了 にします。次にやるべきことは、候補として書きます。 |

## 3.1 Slackなどで直接頼まれた単発の依頼

カードも reviewer もないので、依頼を受けたAIが自分で閉じます。閉じ忘れは、監視が拾います。

| 順 | 内容 |
|---|---|
| 1 | 作業の前に、SSOTへ行を作ります。成果物ごとに1行です(文書1つ、PR1つ、で1行ずつ)。 |
| 2 | 作業しながら、チェックを付けます。 |
| 3 | 最後に、行を読み直し、証拠のある項目だけチェックし、完了レポートを書きます。 |
| 4 | ステータスを 完了 にします。本文の編集では、ステータスは変わりません。ステータスは別の操作で変えます。 |
| 5 | SSOTが 完了 になったことを確認してから、最終の返信を送ります。 |

# 4. SSOTの項目

SSOTに置く行は、タスク、エピック、承認依頼の3種類です。項目は、スクリプトが絞り込みや集計に使うものだけにします。目標値や予算のような長い内容は、本文に書きます。
## 4.1 タスクの行

| 項目 | 内容 |
|---|---|
| タスク名、ステータス | ステータスは 未着手、進行中、レビュー中、完了、キャンセル の5つです。タスクの行に優先度はありません。カードの優先度は決めず、kanban の既定に任せます。 |
| エピック(関連) | 属するエピックの行への関連です。単発の依頼は、これが空です。 |
| 本文の章 | 概要(目的、完了条件、対象外、対象=リポジトリとブランチの4行の表)、やることチェックリスト、作業メモ(1行目にカードID)、完了レポート。担当とエピックは書きません(担当は常に executor、検証は reviewer。エピックは関連プロパティが持つ)。重複確認は作る前に必ず行いますが、記録欄はありません(見つけた場合だけ完了レポートの結果か未確認・残件に書く)。レビュー依頼(再確認してほしい点)は kanban の request-review のコメントに書き、成果物のリンクは完了レポートの該当節に書きます。 |
| 完了レポートの形 | 実施内容、結果、確認した方法、未確認・残件、次のタスク。「なし」だけの章は、未記入と同じ扱いです。 |

## 4.2 michiomochiエピックの行

複数のタスクで1つの目的を追う単位です。目的と進行の全部が、このページに集まります。

| 項目 | 内容 |
|---|---|
| 種別 | プロダクト開発 または 調査。プロダクト開発だけが、工程の行とカードを作る流れに入ります。空は対象外です。 |
| ステータス | 要件定義、設計、実装、テスト、承認待ち、完了、中止の7つです。ステータスは「いまAIがどこまで進んだか」を表し、ゲート制御が書きます(G5)。中止は、人だけが決めます。効果測定はありません。 |
| 新規作成の停止 | 新規作成の停止にチェックがあると、新しいタスクとカードを作りません。これが唯一の機械的な歯止めです。 |
| 本文の章 | 目的(表: 指標、定義、基準値、目標値、期限、完了条件)、候補(チェックリスト。項目名に打ち手を含める)、計測ログ、管理ログ(承認は日付・何を承認したか・決定・レビュー行のURLを1行で残す)、関連ドキュメント、完了レポート。状態の正本は工程の行とステータス属性で、本文には持ちません。 |

## 4.3 工程の行

| 項目 | 内容 |
|---|---|
| 作り方 | プランナーが、エピックごとに、工程の数だけ、最初にまとめて作ります(未着手)。タイトルは工程名だけで、どのエピックかは関連で分かります。 |
| 状態の動き | 未着手、進行中(ゲート制御が開始)、完了(reviewer がAIレビュー合格後に変更)。作業するAIは、工程の行のステータスを触りません。 |
| レビュー中 | 人が判断しなければ進めない場合だけです。レビュー中は、完了ではないので、後ろの工程は待ちます。 |

## 4.4 承認依頼の行(人の判断の窓口)

人が判断することは、全部、この行になります。判断の中身(質問や根拠)はチャットに流さず、行に書きます。ただし、行を作ったときは、該当のやりとりをしているチャット(エピックの「チャット」URLのチャンネルかスレッド)で、みちゃんにメンションして知らせます。チャットが無いときは、新しいスレッドを作ってそこでメンションします(8.2)。

| 項目 | 内容 |
|---|---|
| 名前、本文 | 本文は9章です(判断すること / 推奨 / 人が確かめること / 完了条件の達成状況 / 何を出すか / 残っている危険と未確認 / 根拠(開くページ) / 判断の結果 / 反映の記録、見出しは H1・黄、全体5,000字以下)。リリース承認の行は、リリース判定書の決まった章から ask_human.py --release が機械的に写します(要約は書きません。読めない項目は「未確認：…」と書き、行は必ず作ります)。成果物のリンクは、プロパティではなく本文の「根拠(開くページ)」に置きます。 |
| ステータス | レビュー待ち、承認、差し戻し、取り下げ。承認、差し戻し、取り下げを決めるのは、人だけです。AIは決めません。 |
| 対象エピック | 判断の対象のエピックの行(関連)。種別、優先度、レビュー先、対象タスクのプロパティはありません。今の承認は完了時の1つだけだからです。 |
| キー、反映済み | キーは重複防止です(同じキーでは1回しか作りません)。承認のキーは、エピックのID末尾8桁に -承認 を付けたものです。反映済みは、人の決定をSSOTに反映したあとに、AIがチェックします(同じ決定を2回反映しないための印です)。 |
| 差し戻し後のキー | 元のキーの後ろに、-r2、-r3 を付けて、もう一度頼みます。 |
| 通知 | 行を作った直後に、ask_human.py が Discord へ4行以内で投稿します(リリース承認をお願いします: エピック名 / 推奨: 承認(条件 達成3・一部1・未実施1) / 確かめること: 1件目(ほか n 件) / 行のURL)。宛先とメンションは8.2のとおりです。 |

## 4.5 用意する Notion のデータベース

用意するのは3つで、すべて同じ Notion ワークスペースに置きます。項目名とステータス名は、スクリプトが文字列で検索するので、表のとおりに作ります。名前を変えるときは、スクリプトとスキルも一緒に直します。

| database | 1行が表すもの | 関連 |
|---|---|---|
| michiomochiタスク | 作業1件。工程の行も、このデータベースの行です。 | michiomochiエピックへの関連(単発の依頼は空) |
| michiomochiエピック | 複数のタスクで追う1つの目的 | タスクへの関連(タスク側の関連と対になります) |
| michiomochiレビュー | 人への判断依頼1件 | 対象エピックへの関連 |

### 4.5.1 michiomochiタスク

| 項目 | 型 | 値と用途 |
|---|---|---|
| タスク名 | タイトル | 工程の行は、工程名だけにします。 |
| ステータス | ステータス | 未着手(既定)、進行中、レビュー中、完了、キャンセル。完了とキャンセルは、完了のグループに入れます。 |
| michiomochiエピック | 関連 | 属するエピック。紐づかない派生作業は、プランナーが作りません。カードの優先度は決めず、kanban の既定に任せます。 |
| 作成日時、最終更新日時 | 自動 | 監視が、動きのない進行中を見つけるために使います。 |

本文のひな形(テンプレート)を、データベースの既定のテンプレートにします。章は、概要、やることチェックリスト、作業メモ、完了レポートです。
### 4.5.2 michiomochiエピック

| 項目 | 型 | 値と用途 |
|---|---|---|
| 名前 | タイトル | エピック名 |
| ステータス | ステータス | 軽量版は、要件定義(既定)、設計、実装、テスト、承認待ち、完了、中止の7つです。要件定義から承認待ちまでを In progress、完了と中止を Complete のグループに入れます。現在の実装の値は、案件作成、案件承認待ち、プロダクト要件定義、開発要件定義、開発、QA、リリース判定、効果測定、完了、中止の10個です。承認系の値は、人だけが付けます。 |
| 種別 | セレクト | プロダクト開発、調査。プロダクト開発だけが、工程の行とカードの自動作成の対象です。空は対象外です。 |
| 新規作成の停止 | チェックボックス | チェックが付いている間、プランナーはタスクを作りません。逸脱の検知や予算超過で、自動でチェックします。 |
| チャット | URL | 依頼が来た Discord のスレッドまたはメッセージのリンク(例: `https://discord.com/channels/<guild>/<channel>/<message>`)。エピックを作るエージェントが入れます。分からなければ空にします(推測の URL は入れません)。コードは、この項目が無い DB でも動きます。 |
| タスク | 関連 | michiomochiタスクとの双方向の関連 |
| 管理レベル、会社エピック | セレクト、関連 | 軽量版では作りません。現在の実装にはあります。 |

本文の章は、4.2 のとおりです。既定のテンプレートに、目的の表の枠を入れておきます。

|---|---|---|

| 対象エピック | 関連 | 判断の対象のエピック(エピックの行のID)。成果物のリンクは、プロパティではなく、行の本文の「根拠」に書きます。 |

# 5. 役割

プロファイルは executor と reviewer の2つだけです。全工程のカードは executor が担当し、工程ごとに別のプロファイルにはしません。役割文書A、B、Cは、executor の SOUL に入っている3つの文書で、カードの工程がどれを使うかを決めます。100枚のカードを調べたところ、実行が442回あり、仕組み全体のコストが対話のおよそ3倍でした。役割ごとに別のプロファイルにすると、毎回、同じ前提を読み直すためです。

| プロファイル | 担当する工程 | 現在のモデルの目安 |
|---|---|---|
| executor(役割文書A: PdM) | 要件定義、テスト、リリース判定。PRD、ユースケース、リスク、QAケース、リリース判定書の草稿を書く。 | Sonnet 系、推論の強さは high |
| executor(役割文書B: エンジニア) | 設計、実装。Design Doc、見積もり、実装(git worktree とブランチ)、テスト。PRの作成・公開・マージとデプロイは、しない(スクリプトだけが行う)。 | Sonnet 系の high。Design Doc のカードも同じ。カードに model を指定すると、そのカードのレビューも同じモデルで動くので、工程カードには指定しない |
| executor(役割文書C: アナリスト) | 調査、リリース後の効果検証。SQLの定義文書と、出典付きの所見を作る。 | Sonnet 系の high。根本原因を結論するカードだけ Opus を指定 |
| reviewer | 全工程の検証。自分で再実行して確かめ、完了にするか、差し戻します。生産者の主張を信用しません。 | 最も強いモデル(Opus 系)の high |

| 注意点 | 内容 |
|---|---|
| モデルの偏り | 全員が同じ系統のモデルなので、誤りが相関します。reviewer は、必ず再実行で確かめます。 |
| 前の工程の文脈 | 同じエピックの前の工程で読んだものは、読み直さず、変わった部分だけ取り直します。 |
| 工程が続くカード | 連続して着手できる工程は、1枚のカードにまとめます(1エピック1カード)。1つのセッションが工程を順に進め、reviewer が最後にまとめて、全部の工程の行を完了にします。 |

# 6. ゲート制御の規則

ゲート制御は、AIを使わないスクリプトで、2分ごとに動きます。既定は試し実行(何も書かない)で、反映を指定したときだけカードを作ります。

| 番号 | 規則 |
|---|---|
| G1 | 対象は、種別がプロダクト開発で、ステータスが完了でも中止でもなく、新規作成の停止にチェックがないエピックです。 |
| G2 | 工程の順番は固定です。次の工程は、前の工程の行が、すべて 完了 または キャンセル で、前の工程のカードが1枚も生きていないときだけ始まります。 |
| G3 | 工程の開始は、行を 未着手 から 進行中 にして、カードを1枚作ることです。カードの重複防止のキーは、エピックと工程の組み合わせです。 |
| G4 | エージェントが担当する作業が1つもない未着手の工程の行は、ゲート制御が キャンセル にします。 |
| G5 | エピックのステータスは「いまAIがどこまで進んだか」を表し、ゲート制御が3段で書きます。(1) 完了 でも キャンセル でもない工程の行があれば、その中でいちばん早い工程。(2) 5つの工程の行がすべて 完了 か キャンセル で、リリース承認(レビュー行のキー エピックのID末尾8桁-承認、旧キーは -リリース承認)が 承認 でなければ、承認待ち(人のレビュー待ち。リリース判定の行が未完了のときも、この値で表します)。(3) 5つの工程の行がすべて終わり、リリース承認が 承認 で、その出荷(ship_approved.py。マージされ、登録された repo は本番へ反映済み。出荷の状態が無い旧い承認は、済みとみなす)が済み、生きている工程カードが無ければ、完了。完了と中止は上書きしません。中止 は書きません。 |
| G6 | リリース判定の行が 完了 になったら、リリース承認の依頼(キーは エピックのID末尾8桁-承認、対象エピックにそのエピックを入れる)を、1回だけ作ります。作り方は ask_human.py --release の1本です(差し戻し後の -r2 も同じ)。本文はリリース判定書の草稿の章を機械的に写した9章で、判断すること、推奨、人が確かめること、根拠(判定書への直接リンク)が冒頭と末尾に揃います。ほかの工程(要件定義、設計、実装、テスト)には承認依頼を作りません。ask_human.py --release は、行を作る前に内部で ship_approved.py prepare を呼びます。リリース判定の行の子ページ『PR 本文の下書き』(1行目『タイトル：…』、## 概要／背景／変更内容／検証 の4節、Notion のリンクを残さない)から下書きPR(draft、base main)を作って読み返し、そのあとでレビュー行を作ります。作れないときは行を作らず、理由(no-branch / branch-not-pushed / no-pr-body / pr-body-shape / conflict / no-diff / gh-permission / draft-unsupported)を HELD 行と候補で返します。 |
| G7 | カード作成の途中で失敗しても、記録(ジャーナル)を残し、次の実行で続きから再開します。 |
| G8 | 同時に走らせるのは、1つのエピックにつき1つのカードです。 |

## 6.1 カード本文に必ず入れる内容

カード本文は、テンプレートの文字列置換で作ります。基準となる出力(golden)を保存し、文言を変えたときは、同じ置換を golden にも当てて、テストを通します。

| 項目 | 内容 |
|---|---|
| 前の工程の成果物を読むこと | 前の工程が完了しているから起動したカードです。成果物を土台にして、迷回しません。 |
| SSOTの行を作業ページに使うこと | 新しい行を作らず、工程の行を作業メモと完了レポートに使います。 |
| 自己点検をすること | 3章の5と同じ内容です。 |
| 固い禁止事項 | 7章の内容を、毎回、本文に繰り返します。 |
| 成果物の置き場所 | すべての成果物を、先に、非公開のドキュメント置き場に作り、行と関連づけます。 |

# 7. 守る規則

守る規則は、すべてのAIの指示と、カード本文、スキルに、重複して書きます。1箇所だけに書くと、読まれないためです。

| 規則 | 内容 |
|---|---|
| SSOTが先 | 作業の前に、SSOTに行を作ります。作業のあとに作るのは違反で、すぐに作って、報告に書きます。 |
| PRとデプロイはスクリプトだけ。外部への送信は人の指示まで禁止 | PRの作成・公開・マージとデプロイは、AIはしません。下書きPRはゲート制御が作り、承認のあとの公開・squashマージ・本番反映は ship_approved.py だけが行います(14章)。承認申請と他の人への依頼は、人が明示的に指示するまでしません。ブランチをプッシュするところまでは、自動でします。mainとmasterには、プッシュしません。指示なしにできたPRは閉じますが、本文末尾に <!-- sf-ship --> を持つ下書きPR(ship_approved.py が作ったもの)は閉じません。 |
| 承認は人だけ | 承認を書く、チェックする、承認系のステータスにすることを、AIはしません。 |
| 重複確認(必須) | タスク、エピック、カードを作る前に、SSOT、実行キュー、開いているPRを必ず検索します(記録欄は無く、見つけた場合だけ完了レポートに書きます)。同じ目的と範囲なら作らず、リンクします。 |
| 価値ゲート(必須) | タスクの概要に、次の3つを書けないタスクは作りません。結果で変わる判断。優先度や効果の見積もりが、どこまで動くか。親の指標との関係。 |
| 完了ゲート | チェックリストが全部チェック済みで、完了レポートが実際に書かれているときだけ、完了にします。人の判断が要る項目は、判断が出るまでチェックしません。 |
| 公開と非公開 | 非公開のSSOTへのリンクや名前を、PR、コミット、コードのコメント、共有のチャットに書きません。公開の成果物は、それだけで読めるようにします。 |
| 数字を作らない | 事実、仮説、未確認を分けて書きます。 |
| データ検索の費用 | BigQueryは、先に dry_run を行い、10GBを超える見積もりなら、実行せずに止めます。 |
| 同じ原因で2回失敗 | 止まって、原因を書いて報告します。 |
| 破壊的な操作 | ページやデータの削除は、人が名指しした1件だけ、中身を移したあとにします。取り消しは、ステータスをキャンセルにして、カードも止めます。 |

# 8. 定期ジョブ

この章は本体のジョブです。プラグインが足すジョブは `plugins/<名前>/cron.toml` に書きます。

監視スクリプト付きのジョブは、スクリプトが毎回走り、出力が前回と変わったときだけAIを起こします。出力に時刻を入れないことが条件です(入れると、毎回起きます)。

| ジョブ | 間隔 | AIの使用 | 中身 |
|---|---|---|---|
| 取り込み | 1分 | 出力が変わったとき | 未着手の行を、重複確認してカードにします。コードを求める行は、単発なら実行役のカードにし、エピックが必要な規模なら、先にエピックを作るカードにします。出力が暴走を示したときは、何も作らず、自分で原因を直します。 |
| ゲート制御 | 2分 | 使わない | 6章の規則です。何も作らないときは無出力です。 |
| プランナー | 5分 | 出力が変わったとき | エピックごとに、工程の行を最初にまとめて作ります。候補から、1回に2件までタスクを作ります。タスクが尽きたら、見直しを判断します。 |
| 監視 | 1分 | 警告があるとき | 9章の警告を読み、直せるものは直します。 |
| レビュー結果の反映 | 3分 | 決まった行があるとき | 人が決めた承認、差し戻し、取り下げを、SSOTに反映します。 |
| リポジトリと本番の差の確認 | 1時間 | 使わない | 10章の反映漏れの検知です。差があるときだけ、Slackに通知します。 |
| タスク更新の通知 | 1分 | 使わない | SSOTの前回の状態(スナップショット)と比べて、作成、状態変更、名前の変更、削除を、1行ずつ通知します。最初の実行は、基準を記録するだけです。 |
| 判断待ちダイジェスト | 毎日 9時 | 待ちがあるとき | 人の判断を待っている承認(リリース承認、完了確認、外部送信の指示)を、1通にまとめて思い出させます。待ちが無ければ何も送りません。 |
| 朝会(プロファイル棚卸し) | 毎日 8時 | 毎回 | 実行環境の棚卸しの出力をもとに、自動で採用してよい項目だけを(バックアップを取って)反映し、結果を報告します。 |

## 8.2 承認依頼の通知(メンション)

承認依頼(レビュー行)ができたら、ask_human.py が、行を作った直後に1回だけ Discord に投稿し、みちゃんにメンションします。cron ジョブではなく、行を作る処理の一部です。

| 項目 | 内容 |
|---|---|
| 宛先 | 対象エピックの「チャット」(URL)で決めます。スレッド(またはチャンネル)のURLなら、そこに投稿します。メッセージのURL(依頼元のメッセージ)なら、そのメッセージにスレッド「承認待ち: エピック名の先頭40文字」(1週間で自動アーカイブ)を作って投稿します。そのメッセージに既にスレッドがあるとき(Discord の code 160004)はそのスレッドに、メッセージがスレッドの中にあるとき(code 50024)はそのスレッドに投稿します。「チャット」が空、または Discord のURLでないときは、設定 [chat].fallback_parent のチャンネルに同じ名前の新しいスレッドを作り、そこに投稿します。メッセージのURLと空のときは、投稿したスレッドのURLを「チャット」に書き戻すので、次の承認依頼も同じスレッドに出ます。 |
| 本文 | 4行です(各200字以下、全体2,000字以下)。「<@ユーザーID> リリース承認をお願いします: エピック名」、「推奨: 承認(条件 達成3・一部1・未実施1)」、「確かめること: 1件目(ほか n 件)」、行のURL。自由文の依頼は「承認をお願いします: 行の名前」で始まります。 |
| 設定 | [chat].mention_user(メンションする Discord ユーザーID。無ければメンションせず投稿だけ)と [chat].fallback_parent(--deliver 形式。投稿には channel id だけ使う)。トークンは cron プロファイルの .env の DISCORD_BOT_TOKEN で、ログには出しません。 |
| 失敗したとき | 投稿に失敗しても、レビュー行は残ります(SSOT は Notion)。標準エラーに WARN を出し、終了コードは成功のままです。同じキーの2回目(DUP)は投稿しません。 |

## 8.1 実行キューの設定の目安

| 設定 | 値と理由 |
|---|---|
| カードの割り当て間隔 | 60秒。常駐するプロセスが、準備ができたカードごとに、新しいワーカーを1つ起動します。常駐が止まると、準備ができたカードは、そのまま残ります。 |
| 生きている印 | 15分、印が来ないカードを取り戻します。 |
| 連続失敗の上限 | 2回です。2回続けて失敗したカードは、自動で止めます。 |
| レビューの自動起動 | カードがレビュー待ちになったら、reviewer を自動で起こします。 |

# 9. 監視の警告

警告は、決まった文面の1行です。同じ状態が続くと、段階の番号が増えて、文面が変わります(30分、90分、210分、以降は4時間ごと)。文面が変わるので、直っていない警告で、もう一度AIが起きます。

| 警告 | 意味と対処 |
|---|---|
| ゲート制御の鼓動が10分ない | ゲート制御が動いていません。出力のエラーを読んで直します。 |
| ジャーナルが残っている | カードの作成が途中です。自動で再開します。同じ重複防止のキーで失敗するときは、古い完了済みカードを保管庫に移し、行を未着手に戻します。 |
| 工程の行が進行中なのに、生きているカードがない | カードが完了して、reviewer が承認していれば、行を完了にします。そうでなければ、古いカードを保管庫に移し、行を未着手に戻します。 |
| カードが ready のまま起動しない | 割り当ての停止です。多くは、過去のレート制限のエラー文が残っていて、認証の問題と誤判定されたものです。エラー文を空にすると、1分で起動します。 |
| 順番の違反 | 後ろの工程のカードが、前の工程の完了前に走っています。後ろのカードを止め、原因を報告します。 |
| 未着手の行が10分以上、取り込まれない | 取り込みのジョブを調べて直します。 |
| 進行中なのに、カードも動きもない(15分) | 実行が途中で終わっています。行とチェックリストを、実際の状態と比べて、続きをやります。本当に終わっているなら、完了レポートを書いて閉じます。 |
| 全部チェック済みで進行中のまま、または1つだけ残る | 閉じ忘れです。完了レポートを実際の状態と比べて検証してから、完了にします。報告の言葉だけを信じて閉じません。 |
| レビュー中なのに、承認依頼の行がない | 人に見えない状態です。人が本当に判断するなら、`request_review.py` で承認依頼を作ります(手でステータスを変えません。毎朝の朝会で `check_review_pairs.py` が見つけます)。AIレビューだけの待ちなら、証拠に合うステータスにします。 |
| 公開ページが非公開のDBにリンクしている(リーク) | 自分で直さず、ページと該当の文を報告し、削除を推奨します。 |

| 警告への決まり | 内容 |
|---|---|
| 処理中でも、書き残す | 続きの作業をして警告が出たままにするときは、作業メモに「何が動いていて、何が残っているか」を1行書きます。書いた時刻で、警告が一度消え、本当に止まれば、段階を上げて戻ってきます。 |
| 報告する場合 | 直せなかったとき、人が知るべきことがあるときだけです。「異常なしで進行中」という報告は、送りません。 |

# 10. 変更とデプロイの手順

定期ジョブは、1〜5分ごとに本番のスクリプトを動かします。壊れた1ファイルが、次の1分で全体を止めるので、本番を直接編集しません。

| 順 | 手順 | 中身 |
|---|---|---|
| 1 | ブランチで変更する | main に直接コミットしません。 |
| 2 | テストを足して通す | make test で、SSOT、実行キュー、チャットに触れないオフラインのテストが動きます。警告もエラー扱いです。不具合を直すときは、再現するテストを同じ変更に入れます。 |
| 3 | 本番に置き換えず、全チェックを動かす | make deploy-check。ソースからのコンパイル(警告をエラー扱い)、テンプレートが空でないこと、自己テスト、試し実行の出力が本番と同じ形であること、を確認します。 |
| 4 | PR、CIで make test、マージ | 自分のリポジトリだけは、CIが通ったら自分でマージできます。 |
| 5 | main から make ship(make test のあとに make deploy。deploy 単体はテストを回さない) | バックアップを取り、ファイルを1つずつ原子的に置き換え、置き換え後に自己テストと試し実行をもう一度行います。失敗すると、全部ロールバックします。デプロイの鍵(ロック)が残っているときは、待ちます。削除しません。エピックの変更は、承認のあとに自動で出荷されます(14章)。エピックでない変更だけ、手でこの手順を行います。 |
| 6 | 効いたことを確認する | ゲート制御の鼓動(最後の成功時刻)が進んでいること、ジョブの出力にエラーがないことを見ます。デプロイ直後の10分は、監視が警告を出さない猶予です。 |
| 7 | スキルと指示文も反映する | make deploy が、スクリプトに加えて、スキル(shared/skills)と cron の指示文も、リポジトリを正として本番へ反映します。make sync-check で、差だけを確認できます(差があれば終了コード 1)。 |

| 反映漏れを防ぐ仕組み | 内容 |
|---|---|
| 差の検出と反映 | tools/sync_[live.py](http://live.py) が、リポジトリの skills/ と prompts/ を、本番のスキルと cron の指示文と比べます。--check は差の表示だけ、--apply は反映です。 |
| 毎時の検知 | cron(AIを使わない)が1時間ごとに、本番との差、未コミット、未pushを調べます。差があるときだけ、Slackに通知します。リポジトリを直して反映を忘れた場合と、本番を直接編集した場合の、両方を拾います。 |
| 本番にだけある編集 | 反映すると上書きされるので、先にリポジトリへ取り込みます。本番を直接編集しないことが前提です。 |

| 変更の対象 | 内容 |
|---|---|
| カード本文のテンプレートと golden | 文言を変えるときは、テンプレートと golden に同じ置換を当てます。golden は、新しいコードから作り直さず、古いコードから作ったものを保ちます。 |
| 規則を変えるとき | スキル、カードのテンプレート、役割の指示、定期ジョブの指示文の、すべてを同時に直します。規則を持つ場所が複数あるためです。 |
| 定期ジョブの指示文 | リポジトリの prompts/ に元のファイルを置きます。本番への反映は make deploy(または make sync)が、hermes cron edit で行います。手で反映する運用は、反映漏れを起こしたので、やめました。 |

# 11. 軽量版の工程(別環境向け)

会社のエピックと工程ガイドライン(提出物、リーガル、CS、マーケの洗い出しなど)は外します。工程は5つ、人の承認は完了時の1つにして、仕組みは同じままにします。

| 項目 | 現在 | 軽量版 |
|---|---|---|
| エピック | 会社のエピックと、非公開の michiomochiエピックの2層 | michiomochiエピックの1層だけ。会社エピックの関連と、公開と非公開の分離は外します。 |
| 工程 | 案件作成、プロダクト要件定義、開発要件定義、開発、テスト、リリース判定(リリース後作業は、人が効果測定にしたときだけ追加) | 要件定義、設計、実装、テスト、リリース判定の5つだけです(効果測定とリリース後作業はありません)。 |
| 人の承認 | 案件承認、要件定義のレビュー、リリース判定書の承認の3つ | リリース承認(リリース判定の完了時)の1つ。要件定義、設計、実装、テストは、AIレビュー(reviewer)だけで進みます。 |
| 工程ごとの成果物 | PRD、ユースケース仕様書、リスク、リーガル、QAケース、Design Doc、見積もり、テスト計画、リリース計画、リリース判定書など | 要件定義: 要件書。設計: 設計書と見積もり。実装: ブランチと実装メモ。テスト: テスト計画と結果。リリース判定: 判定書の草稿とPR 本文の下書き。 |
| 会社側の工程タスク | プランナーが、会社のタスクDBに、工程ごとのタスクを作る | 不要です。工程の行のチェックリストに、工程の成果物を並べます。 |
| 管理レベル(L1、L2、L3)の判定 | 別プロジェクトのスキルで暫定判定し、最終は人が決める | 不要です。単発は、そのまま実行役のカードにします。大きな変更は、先にエピックを作ります。 |
| 案件作成の軽い道 | 目的の表と打ち手を含む候補がすでにあれば、案件作成の行を完了で作る | 要件定義の行で同じにします。目的の表と、打ち手を含む候補が揃っているなら、最初から完了にします。 |

## 11.1 軽量版でも外さないもの

| 項目 | 理由 |
|---|---|
| SSOTが正本、行が先 | 進捗が、チャットやカードに散らばらないようにするためです。 |
| AIを使わないゲート制御 | 工程の順番と、重複したカードの防止を、確実にするためです。 |
| 独立した reviewer と完了ゲート | 実行役の自己申告で完了にしないためです。 |
| 外部送信の禁止 | 間違った依頼やメールが、取り返せなくなることを防ぐためです。PRは、人が承認するまで下書きのままです。 |
| 重複確認と価値ゲート | タスクの増殖を防ぐためです。 |
| 監視と、出力に時刻を入れないこと | 止まりに気づく仕組みと、AIの起動コストを抑える仕組みのためです。 |
| デプロイの手順、反映漏れの検知、オフラインのテスト | 定期ジョブが、壊れた変更で止まらないようにし、リポジトリを直したのに本番が古いまま、という状態を防ぐためです。 |

# 12. 導入の順番

小さく作って、1段階ごとに検証します。現在の仕組みは、この順で作ったものではなく、運用しながら育ったものです。再現するときは、次の順が安全です。

| 段階 | 作るもの | 完了の確認 |
|---|---|---|
| 1 | SSOT、ルール文書 | 依頼を1件、手で登録でき、ステータスが5つで動く。 |
| 2 | 実行役、レビュー役の指示 | 小さな依頼を1件こなし、reviewer が検証して完了にできる。根拠のない完了レポートは、差し戻される。 |
| 3 | 取り込みと実行キュー | 依頼の登録から5分以内にカードができ、同じ依頼から2枚目ができない。 |
| 4 | ゲート制御 | オフラインのテストで、順番、重複防止、途中失敗からの再開、新規作成の停止が確認できる。 |
| 5 | 承認の窓口と反映 | 承認が、同じキーで1回だけ作られ、承認、差し戻し、取り下げがSSOTに反映される。 |
| 6 | プランナーと監視 | 疑似データで、止まったカード、順番の違反、閉じ忘れを検出できる。 |
| 7 | 変更とデプロイの手順 | 壊れたファイルを本番に反映しようとすると、テストで止まり、本番は変わらない。 |
| 8 | 通しの確認 | 小さな本物の依頼が、5工程を順に進み、リリース承認が人に届き、完了レポートが残る。 |

# 13. 運用での注意点

現在の運用で、実際に起きたことから得た注意点です。

| 注意点 | 内容 |
|---|---|
| SSOTの項目やステータス名は、人が運用中に変える | 作成や更新の前に、スキーマを読み直します。名前を変えたら、スキル、ルール、定期ジョブの指示文を、全部検索して直します。 |
| 子のアカウントが、親の認証を引き継がない | 実行役ごとのプロファイルは、SSOTやデータ基盤への認証を持たないことがあります。認証の保存先を共有します。 |
| 共通のスキルは1箇所に置く | プロファイルごとにコピーすると、ローカルのコピーが優先されて、静かにずれます。 |
| 人の判断の項目を、AIが勝手にチェックした | 完了ゲートで防ぎます。人が決める項目は、決定があるまでチェックしません。 |
| ステータスは本文ではなく属性 | 本文を編集しても、ステータスは変わりません。完了にするときは、ステータスだけを別の操作で変え、読み直して確認します。 |
| レート制限のあとで、カードが起動しない | 9章の ready のままの警告を見ます。レビュー待ちのカードも同じ状態になります。 |
| 各工程が遅いとき | 時間を測ってから直します。大きいのは、最初の1回の作業(およそ半分)と、修正が小出しになるレビューの往復です。工程は、直列のままにします。並列にしません。 |
| 取り消しは、SSOTと実行キューの両方で | SSOTだけキャンセルにすると、ワーカーが動き続けて、ページを書き直します。 |

# 14. 出荷(承認後の公開・マージ・本番反映)

人がリリース承認の行を 承認 にしたあとの、下書きPRの公開、squashマージ、本番への反映は、AIを使わないスクリプト ship_approved.py が行います。cron「SF 出荷(3分)」が ship_approved.py run を3分ごとに流します。人の入力は、レビュー行のステータスだけです。

| 項目 | 内容 |
|---|---|
| 依頼を作るとき | ask_human.py --release が内部で ship_approved.py prepare を呼び、リリース判定の行の子ページ『PR 本文の下書き』から下書きPR(draft、base main)を作って読み返します。そのあとでレビュー行を作ります。作れないときは行を作らず、理由を HELD 行と候補で返します(6章の G6)。 |
| 承認のあと | main に重ねた make test → 下書きの解除 → head の SHA を指定した squash マージ → リモートのブランチの削除 → main の作業ツリーで make ship → make check → make smoke。結果は、レビュー行の『反映の記録』、PRのコメント、ハブの管理ログに書き、反映済みにチェックを入れます。エピックの完了は、出荷が done になってからです。 |
| 状態 | drafted → tested → readied → merged → deployed → done。行き止まりは、rejected(差し戻し。PRは下書きのまま、コメントは1回で理由は書かない)、withdrawn(取り下げ。PRを閉じ、ブランチは残す)、void(マージ前に崩れた)、halted(マージのあとに承認が変わった。本番反映を止める)、deploy_failed(マージのあとの失敗)。見方は ship_approved.py status です。 |
| マージ前に崩れたとき | head が動いた、コンフリクト、テストが赤、チェックが赤のときは、マージせず下書きに戻し、候補を足します。直ったら -r(N+1) で出し直します。 |
| マージ後に失敗したとき | main は戻しません。deploy_failed になり、人が ship_approved.py retry を流すまで待ちます。 |
| ロック | 出荷の実行は ship_approved.lock で重ならないようにします。本番反映は、デプロイ自身のロックを使います。ロックが取れないときは、次の回に回します。 |
| CIを待たない理由 | GitHub Actions は一度も動いていません。待っても結果が来ないので、マージ前の検査は、main に重ねて手元で流す make test(14.4秒)にします。 |
| 自動で rebase しない理由 | コンフリクトを機械で直すと、人が見ていない変更がマージされます。コンフリクトは void にして、直す作業を候補に足し、人が承認したものと違う内容は出しません。 |
| 本番反映の登録 | factory.toml の [ship.repos."owner/repo"] に、test、deploy(順に流すコマンド)、cron_paths、describe を書きます。登録の無い repo は、マージまでです。 |
| 公開される場所 | PRのコメントとコミットには、Notion の名前もリンクも書きません。 |

# Gate controller: how phase cards get created, and why a pipeline stops

Use when you reason about how cards start, set up a board or cron delivery, or answer 'why is it stopped?'.

## Gate controller (how phase cards get created)
- Terminology: the hub row of the エピック DB is the epic's management page; say 'epic' (エピック) in every message to the user and in Notion pages, and define any coined term the first time you use it.
- Registry (hub): a row in the エピック DB with 種別 プロダクト開発 declares that the epic is managed by the pipeline. Epics whose 種別 is not プロダクト開発 are never touched by the phase flow. Create rows with `create_row.py` (it applies that DB's default template; body chapters: 目的 (table), 候補, 計測ログ, 管理ログ, 関連ドキュメント, 完了レポート). The gate controller manages every hub row whose ステータス is neither 完了 nor 中止 and whose 新規作成の停止 is unchecked. The state of a gate or phase lives only in the phase rows and the hub ステータス (not in the page body); the page body keeps 管理ログ, with one line per human decision (date, what was approved, decision, review row URL). Derived tasks link to the hub row through their エピック relation.
- Board: one board `${board}` (a board is NOT an epic; epics are separated by tenant `epic-<last 8 hex of the hub row id>`). A board slug is immutable: to rename, `hermes kanban boards export <old> -o f.tar.gz`, `boards import f.tar.gz --as <new>`, then `boards rm <old>` (archives, recoverable) and update every reference (skills, SOUL, cron prompts).
- L1 tasks (an epic only as a container; scripts/levels.toml gives L1 no phase rows, so the gate controller and the planner skip it by its レベル, no flag): the intake cron (monitor mode, ステータス 未着手) makes the card for the executor. Do not reintroduce a per-task class field; the epic and レビュー中 already carry that meaning.
- Controller: ${live}/epic_gate_controller.py (deterministic, no LLM; --apply creates cards, default is dry-run, --assume-status=<ステータス> simulates a gate in dry-run). The gate controller cron runs epic_gate_apply.py every 2 minutes, silent unless it creates or fails; its delivery goes to the chat thread (see Notifications).
- Rule: progress follows the phase rows (task rows '<フェーズ>' linked to the hub, made by the gate controller from levels.toml when the epic has none: `create_epic_rows`, once; an epic that already has rows is never touched): the gate controller starts the next phase (row 未着手 -> 進行中, role by PHASE_ROLE; with MERGE_PHASES the first startable phase and every later contiguous phase whose row is 未着手 and has agent processes share ONE card keyed `phase-<epic>-<ph1>+<ph2>+...`, the reviewer sets all its rows 完了 in one pass) only when every earlier phase row is 完了 or キャンセル (レビュー中 is not finished: a person must decide; only the reviewer sets 完了 after the AI review) and no live card of an earlier phase exists. Order: 要件定義, 設計, 実装, テスト, リリース判定.
- Tenant `epic-<last 8 hex of the hub row id>` (the first 8 hex collide for epics created around the same time).
- Limits: no approval record is read any more, so nothing in the pipeline stops work that a person would have blocked at a gate; the hard rule above (the AI creates, publishes or merges no PR and deploys nothing; no requests to others) is the only fence and is repeated in every card body. If you change the phases, update the ORDER/HUB_PHASE_STATUS/PHASE_ROLE tables in epic_common.py.

## Diagnosing a stalled pipeline ("why is it stopped?")
The hub ステータス and the gates are NOT the cause (standing policy: no approval gate blocks agent work), so do not answer with "waiting for an approval". Walk the chain instead:
1. Hub phase rows: find the first row that is not 完了/キャンセル. The controller starts the next phase only after the reviewer sets that row 完了.
2. Card of that phase: `hermes kanban --board ${board} list` (grep the tenant `epic-<8 hex>`), then `show <id>`. A card sitting in `review` with a stream of `respawn_guarded {'reason': 'blocker_auth'}` events means the reviewer is never started.
3. Cause: `check_respawn_guard` (hermes-agent/hermes_cli/kanban_db_dispatch.py) returns blocker_auth when tasks.last_failure_error in the board DB (`~/.hermes/kanban/boards/${board}/kanban.db`) matches quota/rate-limit/429/auth words and the latest run is not rate_limited/crashed. A stale 5-hour-limit message from an earlier worker keeps matching after the quota has reset, so it is not an auth problem. Check the profile's real auth only if the text is genuinely auth-related.
4. Fix: once the quota has reset, back up then NULL the column for the stuck review cards (`update tasks set last_failure_error=NULL where id in (...) and status='review'`), wait ~90s, and confirm the reviewer run shows owner_admitted/heartbeat events.
Report with the cause and the evidence; never present the ticking of approval packs as the next step.

## Notifications
Every cron job (including no-agent ones such as the gate controller) delivers to the chat channel #開発 (${failure_deliver}), pipeline jobs to the dedicated thread (${deliver}); set it with `hermes -p ${cron_profile} cron edit <id> --deliver ${deliver} --failure-deliver ${failure_deliver}` when creating a job. Agents report in the same thread.

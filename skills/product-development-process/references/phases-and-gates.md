# Phases, order of work, gates and release evidence

Use when you start a new initiative, write a phase deliverable, prepare the リリース判定, or deal with a PR that exists ahead of its gate. The rules that must not be missed (core rule, deliverable location, release-type actions, UI images) are in SKILL.md.

## Order for a new initiative
1. Investigate with data: existing Notion pages, the repo, logs. Write reusable findings as child pages of the task row. State facts, hypotheses and unverified items separately.
2. Duplicate check (mandatory, see Duplicate check in autonomous-task-execution): Notion search over エピック and タスク, the kanban board and open PRs for an initiative with the same goal or scope. Read the hits (no record row is kept; write a finding only in the 完了レポート 結果 or 未確認・残件, or the hub's 管理ログ for an epic); if related, link instead of creating a new epic; if the same, continue the existing one.
3. Create the epic hub row with `python3 ${live}/create_row.py --spec <spec.json>` (kind epic; spec fields, the exit codes and the checks: autonomous-task-execution references/epic-creation-from-request.md, steps 4-5). The spec sets 種別 プロダクト開発 or 調査 and チャット = the URL of the Discord thread/message the request came from (leave it out if you do not know it, never guess a URL); never build the page by hand. Fill 目的 (table) and 候補 (each item names its 打ち手) with real content. Epic ステータス starts at 要件定義; afterwards the gate controller writes it from the earliest unfinished phase row. State 期日 and unknowns as unconfirmed; never guess them.
4. Size the work by the judgement criteria in SKILL.md (a small change is an L1 task: `create_row.py --level L1`).
5. Continue phase by phase; each phase's deliverables are the items of its row (levels.toml). Read a template's own 'ask for approval before writing' step as: write the plan into the task's 作業メモ (and, for a gate, link the deliverable in the hub's 関連ドキュメント) and proceed with reversible drafts; do not wait idle, but never mark reviews or approvals as done.
5b. Depth of deliverables (mandatory): never write '要確認' as a placeholder. For an open question name who answers it and what changes the answer; for something not applicable state the reason and the condition that triggers a re-check. Link only to pages you fetched (copy ids from the result, never from memory).
5c. Checklist: the deliverables of a phase are the items of the phase row's やることチェックリスト (the gate controller writes them from levels.toml); there are no separate company-side tasks. The phase card works the items in order and the reviewer verifies them.
5c-auto. The gate controller checks every registered epic and, when it has no row yet, creates its rows from levels.toml itself (the planner makes none; no human step). Only epics whose 種別 is プロダクト開発 are in scope (phase rows and phase cards); 種別 調査 or unset epics are never touched by these flows. Do not wait for a recorded decision.
6. Every code change links its epic in the private records. An agent never creates a PR: keep the work as pushed branch commits and a drafted PR 本文の下書き; the gate controller opens the draft PR from it when the release ask is made. The PR body never contains private Notion URLs (see Private vs public in autonomous-task-execution).

## Gates (evidence, not claims)
Standing policy overrides phase-by-phase gating for agent work (see Core rule in SKILL.md): agents do not wait for an approval before working up to リリース判定, but they never write approvals, never ask for them except through the gate machinery, and never act on release-type steps without them. The approval is given by a person in the レビュー DB (row ステータス 承認); agents treat it as given only by the rules in SKILL.md (Release-type actions).
- Publishing the draft PR, the merge to main and the production deploy of an approved release are done by ship_approved.py after the person's 承認, never by an agent. Before other release-type actions (tag, production configuration change) re-read the hub: the リリース承認 record must exist. If not, stop, set the task レビュー中 (with its review row) and write the missing records and the points to re-check in the comment of `hermes kanban request-review`. Even with all records present, these actions are executed only on a person's explicit instruction.
- The 判定書の草稿 follows the template of its level (`judgement_template` in levels.toml, under `${live}/templates/`); the first line of 推奨 is 推奨：承認 or 推奨：差し戻し; the 状況 words are 達成・一部・未達・未実施・対象外. `ask_human.py --release` copies the chapters mechanically and `finish_rows` will not complete the row while its PROBLEMS list has a 未確認 line; check it yourself with `python3 ${live}/ask_human.py --release --epic <hub row id> --key test --dry-run`.
- UI image check, mechanism (the rule is in SKILL.md): the gate controller checks it with ui_evidence_verdict (epic_common.py); when an image is missing it creates no review row, writes the reason to the hub's 管理ログ, adds a 候補 item (the planner then makes the task that adds the images), comments on the リリース判定 card and posts one HELD line. The review row copies the 判定書's chapters (each up to its limit) with the same images (uploaded to Notion, never an external URL) and links the 判定書 directly in its 根拠（開くページ） chapter. Write 'UI 変更：なし' in the 判定書 when nothing on screen changes; it never overrides a UI path in the diff.
- Requests to other people (reviewers, other teams) are prepared as a draft (a child page of the task row, linked in the 完了レポート) for a person to send. Do not send or approve anything yourself.

## Artifacts produced ahead of their gate
Under the standing policy, the AI creates no PR; the only PRs are the draft PRs ship_approved.py opens, whose body ends with `<!-- sf-ship -->`: never close those. If any other PR (even a draft) already exists without ${owner}'s instruction, close it with a public comment (never delete the branch), keep the branch as a resume note in the task row, and archive the old card and reset the phase row to 未着手: the controller creates cards only for phase rows that are 未着手, so never leave such a row 進行中 without a live card.

## Reporting
When a phase deliverable is ready, put the links directly in the matching section of the task's 完了レポート; when a human gate is next, link what to review in the hub's 関連ドキュメント (the person decides in the レビュー DB row); put review requests for the AI reviewer in the comment of `hermes kanban request-review`. Keep facts, proposals and unverified items separate.

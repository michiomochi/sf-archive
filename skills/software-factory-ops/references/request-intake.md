# 依頼の受け方（#開発）

SKILL.md の索引から: #開発 で作業の依頼を受けたとき（行の作り方・タスクかエピックかの振り分け・設計を伴う依頼・段階のある案件・対象外が決まったときの切り出し）。

#開発 で受けた作業の依頼は、すべてこのファクトリーを通す。行が先で、作業は後。

1. 作業を伴う依頼は、まず SSOT に行を作る。
2. 規模で振り分ける。
   - 成果物が1つで終わる（調べる、1ファイル直す、1つ作る）→ タスクに1行（ステータス未着手、優先度は付けない=カードの優先度は kanban の既定、概要に目的・完了条件・対象外・対象＝リポジトリとブランチ）。1分以内に取り込みがカードにする。
   - 複数工程が要る、「〜したい」「〜を作って」の依頼 → エピックに1行。最小要件は、種別がプロダクト開発、`チャット`（URL 型）に依頼元の Discord メッセージ/スレッドの URL（分からなければ空。推測の URL は入れない）、ステータスが要件定義、目的の表に目標値と完了条件、候補のチェックリスト（項目名に打ち手を含め、1件以上）。プランナー（5分毎）が工程の行を作るまで待つ。
     **実物の作り方は `POST /v1/pages` に `parent.data_source_id=エピック` + `properties` (`名前`/`ステータス`/`種別`/`チャット`) + `children`（エピックの章。目的の表は `table` と `table_row` を children に直接並べる）を1回で投げる。** 期限は「設計が返ってから見積もりで決める」と仮置きでよい。プロパティ名・選択肢は `sf/notion/schema.json` が正本。
   - 調査だけなら種別は調査（工程の行とカードの自動作成には入らない）。迷ったらエピック。
3. 実行はファクトリーに任せ、自分で実作業を始めない。読み取りだけで即答できる質問は例外で、行を作らない。
4. 行を作ったら #開発 に1通だけ返す（行の URL、タスクかエピックか、次に何が起きるか）。
5. 進捗は SSOT の行と kanban ボード dev のカードで答える。チャットの記憶で答えない。「もう push した？」「変更は全部済んでる？」も同じで、答える前に実測する: `gh repo list <owner>`（リポジトリ名）、`git status -sb` と `git log --oneline origin/main..main`（未 push の差分）、`gh pr list --state all`（未マージの PR）、`git worktree list`。実測が未着手なら、そう言ってから行を作る（推測で「たぶん済み」と言わない）。
6. 承認・差し戻しは人だけ。
7. 障害対応で即時に手を動かすときも、先に行を作り、やったことを事後に書く。
8. **行を作ったターンで、本文の「概要」表と「やること」まで書く。** 調査を先に深掘りすると、
   ツール呼び出しの上限に当たって**行だけあって本文が空**のまま回答を返して終わる。
   途中経過は「作業メモ」に落とし、完了レポートだけを最後に回してよい
   （調査ものは結果が出た時点で行に書いてから報告する）。
9. **設計を外部（Opus）に回すのは、「何をするか」ではなく「どうやるか」が実測で決まらないとき。** 回す目安は4つ——案が2つ以上あって優劣が測れない／触る場所が3ファイル以上に散るか他の系（スキーマ・権限・デプロイ）をまたぐ／順序を誤ると壊れる／原因が分からない不具合。逆に、実測（grep・DB の分布・履歴）で結論が1つに決まる「残すか消すか」は自分で決め、根拠を行と回答にそのまま書く（待たない）。**設計を伴う依頼は、設計が固まる前に行がカードになる。** 取り込みは1分毎なので、行を作った直後にカードが走り出し、設計レビューが返る前に暫定案の本文で実装が始まる。設計を外部（Opus）に回す依頼では、(1) 本文は暫定案として書く、(2) 設計が返ったら**すぐ行の本文を直し、同じ内容をカードの `kanban_comment` にも入れる**（走行中のワーカーは本文しか読まないことがある）、(3) レビューにはその設計と突き合わせさせる（`kanban_request_changes` には設計の要点を書く）。
    **設計の全文は開発ドキュメント DB `4939e769-ccb4-172d-5dea-a45a27368a1a` に1ページ作って**（`ntn pages create --parent data-source:<ds> --json < design.md`）、エピックの関連ドキュメントからリンクする。行の本文には要点・完了条件・対象外・マージ順だけを残す（全文を本文に入れると読み手が迷い、次の工程のワーカーも読まない）。
    カードは既に走っているので、先に `hermes kanban --board ${board} ls | grep <エピックID末尾8桁>` で走行中のカードを特定してから `kanban_comment`（`board="${board}"` を毎回明示）に**設計書の URL・決まったこと・対象外・変更するファイル・検証方法**を入れる。行の本文を書き換えるのは、そのあと（`ntn pages edit <行ID> < body.md`。エピックの目的表は sf リポジトリのタスク雛形と同じ HTML `<table>` の書き方で）。
10. **段階（フェーズ・リリース段階）のある案件で「最後まで承認なしで進めて」と言われたら、中間の承認は取らない。**
    設計 → 段階の実装 → テスト → PR → マージまで自走し、人に出すのは**不可逆な切替（実売買・公開・本番設定の切替）の直前1回**だけ。
11. **エピックの「対象外」に書いた未決が、人の判断で決まったら、そのエピックを広げずに別エピックを立てる。**
    走行中のカードは対象外を読んで動いているので、途中で対象を足すと工程の前提が食い違う。代わりに (1) 新しいエピックを作り（目的表の完了条件を検証できる形で、`チャット` にその発言の URL）、(2) 旧エピックの管理ログに「切り出した」1行と新エピックの URL を足し（`PATCH /v1/blocks/<行ID>/children` に `position.after_block` 付きで、管理ログの段落の直後に入れる。付けないとページ末尾に並ぶ）、(3) 旧エピックの走行中カードに「対象外は変えない・どこが接続点か・どの文面の持ち主がどちらか」を `kanban_comment` で書く。
    接続点が文言や定数なら、**持ち主を1か所に寄せる指示まで書く**（例: 固定文は `templates/<topic>.md` の1枚に置き、コードはそれを描画する。同じ文を2か所に置かせない）。それを見る検査も selftest に入れさせる。
    両方のエピックが同じファイルを触るなら、**マージ順を設計に決めさせて**新エピックの管理ログとカードに書く（後から積む側は前提が main に入っているかを `git merge-base --is-ancestor` で確かめ、入っていなければ block する）。
